Reading the numbers: the whole beats path (analysis plus placement) is far cheaper than any stretcher, and analysis runs once per source, not per tempo change. Per-tempo-change work is the cut-and-place step, which is effectively instant. Rubber Band R3 and Signalsmith default are fast enough for a proxy rendered in the background on a 3-minute source (under half a minute); none of them is needed on the audio thread, because stretched clips play from a proxy. The Rubber Band numbers come from the built-in FFT of the single-file build; an optimised FFT would be faster. Debug build for reference (the benchmark target is `/O2` but the libraries use checked iterators): 3 to 4 times slower.

**Listening note (2026-10-09):** the user listened to the 4-bar results that `StretchBench --out <folder>` writes (original, `rubberband_r2/r3`, `signalsmith_default/cheaper`, `beats_prototype`) and judged the beats prototype to sound OK. No problems were reported with the 3 ms fades, the silent gaps when slowing down or the cut-off tails when speeding up. Task 7.2 is done.

## Other observations

- Engine startup: right after the engine is constructed there is no wave output device in the engine. Playing then makes the transport start and stop itself within 0.15 s (position stuck, playing=0). After the startup scan it works. M1 must wait for the device manager to finish before loading or playing (or reallocate the playback context when devices appear).
- Engine output device defaults: it also opens an audio input by default (this PC has an ASUS Xonar input). Switched off with an engine-behaviour override until M8 (input recording).
- Render tasks need a UI behaviour that runs them (the default does nothing): `runTaskWithProgressBar` runs the job on a thread while pumping messages. Without it `renderToFile` returns nothing.
- Rubber Band is now built into the Tracktion module (`external/rubberband` v4.0.0, single-file build, `TRACKTION_ENABLE_TIMESTRETCH_RUBBERBAND=1` and `TRACKTION_BUILD_RUBBERBAND=1` on `sampler_engine`, CMake option `SAMPLER_RUBBERBAND`). Without it Tracktion's stretch mode is `disabled`. The single-file build uses Rubber Band's built-in FFT, and Rubber Band is GPL: fine under the AGPLv3 plan.
- Endpoint loopback records what the device plays after the Windows volume is applied: a tone at 0.2 FS arrived at 0.004 (device volume low), and a different level on the next run after the volume moved. Process loopback delivers the signal before the volume (full level). Process loopback is therefore also the better recording path.
- Loopback sends no packets while nothing plays; process loopback sends continuous (silent-flagged) packets, endpoint loopback does not. Gap filling from packet QPC timestamps handles both.
- Plugin hosting was in process (the spec allows a plugin failure to close the app). Only our JUCE test plugin was tried: no instability seen in 7 test cases, including a 33 s real-time run and a save/reopen in a second engine. No third-party VST3 was available (Surge XT and Kontakt 7 Player are not installed, the Native Instruments plugins here are VST2 only), so task 6.6 (separating host faults from plugin faults) had nothing to separate.
- **Maschine-specific checks deferred to M5** (Maschine 3 not owned / no VST3 on this PC): very large state chunks (save size and time, undo, autosave every minute), editor resize (Maschine's window is resizable and large), pattern drag-out (dragging a pattern from the plugin onto the timeline: needs a native drag-and-drop bridge, not tried), plugin activation and licensing prompts, and many outputs (16 pairs; we tested 4). R14 stays open until then.
- Real-time test notes: it plays 16 bars through the default output and records them with endpoint loopback (so other audio playing on the PC at that moment would add noise); it skips itself when there is no output device or the device plays silence.
- Waiting for the output device is not enough before playing: the engine also needs its startup scan to finish (the test waits 2.5 s after the device opens), as noted above.
- Test plugin: build target `SamplerTestPlugin_VST3` (JUCE `juce_add_plugin`, static runtime); it exports `sampler_testplugin_processBlockCount()` so tests can count host calls.
- JUCE pinned to the commit Tracktion v3.2.0 pins (8.0.6 + 19 commits), not 8.0.15.
- Debug presets: `juce_recommended_config_flags` adds `/Od`, which cancels `/O2`; the engine target does not link it.
